# Seqr — Design Spec

**A local-first, end-to-end-encrypted peer-to-peer chat for small circles of friends, supporting both 1:1 and group conversations.**

Date: 2026-06-26
Status: Approved design (pre-implementation)

---

## 1. Goal & scope

Seqr is a cross-platform desktop application (Linux, Windows, macOS) for private, end-to-end-encrypted (E2E) messaging between friends. It is local-first: all message history lives encrypted on the user's own device, and message content is never readable by any server.

**In scope for v1:**

- Local user account, unlocked by a password the user sets (with opt-in auto-login).
- A chat dashboard: conversations list on the left, active chat window on the right.
- 1:1 conversations between two friends.
- Group conversations with multiple friends.
- Per-conversation encryption with a shared symmetric key; any member may rotate or revoke the key, taking effect for all members.
- Adding friends by exporting/importing a profile blob.
- Adding members to a group; removing members from a group.
- Encrypted local message history per conversation.
- Offline delivery via an encrypted mailbox hosted on the user's own VPS.
- A self-hosted helper service (rendezvous + relay + mailbox).
- A README covering per-OS install, helper hosting, and the add-a-friend / group walkthrough.

**Explicitly out of scope for v1 (YAGNI):**

- Forward secrecy / per-message ratcheting (compensated by manual rotation — a deliberate trade).
- Federation, multiple identities per install, or directory/discovery servers.
- Voice/video, file transfer, reactions, read receipts (may follow later).
- Mobile clients.

## 2. Technology choices

| Concern | Choice | Rationale |
|---|---|---|
| Desktop shell | **Tauri** | Small binaries, Rust core, best library fit for P2P + crypto. |
| Core language | **Rust** | First-class crypto and P2P crates; secrets stay in a memory-safe core. |
| UI | **Preact + SCSS** | Per house style: hierarchical SCSS, one `.scss` per component, real class names, no CSS-in-JS, tab indentation. |
| P2P transport | **iroh** | Direct hole-punched QUIC with blind relay fallback; matches the chosen transport model. |
| Key agreement | **x25519-dalek** (X25519 ECDH) | Derive shared secrets on-device; only public keys are ever transmitted. |
| Message authenticity | **ed25519-dalek** (Ed25519 signatures) | Per-sender signatures — required so group members cannot forge each other. |
| Message sealing | **ChaCha20-Poly1305** (AEAD) | Authenticated symmetric encryption of message payloads. |
| Password stretching | **Argon2id** | Derives the local vault key from the login password. |
| Local storage | **SQLCipher** (encrypted SQLite) | Whole-database encryption at rest, unlocked by the vault key. |
| Secret storage (auto-login) | OS keychain (Keychain / Credential Manager / Secret Service) | Stores the vault key when auto-login is enabled. |
| Helper service | Small standalone **Rust** binary | Rendezvous + relay + mailbox; stateless of plaintext; holds no accounts. |

## 3. Security model

### 3.1 Identity

Each user holds, inside their encrypted vault:

- A long-term **X25519 keypair** (for ECDH key agreement).
- A long-term **Ed25519 keypair** (for signing messages).
- An **iroh node identity** (network address / node id).

### 3.2 Profile blob (the unit of "adding a friend")

A compact, serialisable blob containing **only public data**:

- X25519 public key
- Ed25519 public (signing) key
- iroh node address (how to reach this peer)
- Display name (user-chosen label)

The profile blob carries **no secret key material** and is safe to transmit over any channel. Exported as a copyable string and a file; QR is a later addition.

### 3.3 Conversation = roster + key + epoch

The central abstraction. A **conversation** is:

- a **roster** of members (each member = X25519 pubkey + Ed25519 pubkey + node address),
- a **current symmetric key**,
- an **epoch** number (monotonic; increments on each rotation),
- a **type**: `Direct` (exactly two members) or `Group` (two or more).

A 1:1 chat is a degenerate group of two; the same data model and UI serve both.

### 3.4 Key agreement strategies (`KeyAgreement` trait)

Two implementations behind one interface:

- **`DirectKey`** (1:1): the symmetric key is derived directly via `ECDH(my_x25519_priv, their_x25519_pub)`. No distribution step — both sides compute the same secret independently. Rotation re-runs ECDH with fresh ephemeral keys exchanged over the existing secure channel.
- **`GroupKey`** (group): a random symmetric group key `Kg` is generated by one member and **distributed individually** to every other member, each copy sealed under the pairwise ECDH secret between distributor and recipient:

  ```
  for each member M in roster (excluding self):
      envelope = seal( ECDH(self_x25519_priv, M_x25519_pub), Kg )
      deliver envelope to M   (direct, or mailbox if offline)
  ```

  Because each envelope is sealed to one recipient, only that recipient can open it. This requires **every group member to be friends with every other member** (i.e. hold each other's public keys), which is established when a member is added (see §3.7).

Both strategies yield a "current symmetric secret" consumed identically by `crypto.seal` / `crypto.open`.

### 3.5 Message sealing and authenticity

Every outgoing message is:

1. **Sealed** with the conversation's current symmetric key using ChaCha20-Poly1305 (confidentiality + integrity against outsiders).
2. **Signed** with the sender's Ed25519 key (authenticity — proves *which member* sent it).

In a 1:1 the pairwise key already authenticates the single counterpart, but signatures are applied uniformly so the path is identical for both conversation types. In a group, the signature is what prevents one member from forging a message as another, since all members share `Kg`.

A message frame contains: conversation id, epoch, sender id, sequence number, signature, ciphertext.

### 3.6 Rotation and revocation

- **Rotate (1:1):** either party generates a fresh ephemeral X25519 keypair, sends the new public key over the existing encrypted channel; both derive a new shared secret; old secret destroyed; epoch increments.
- **Rotate (group):** any member mints a new `Kg`, distributes sealed envelopes to all current members (§3.4), epoch increments, old `Kg` destroyed.
- **Remove member (revoke, group):** the remover mints a new `Kg` and distributes it to everyone **except** the removed member, who is thereby cut off from all future messages. Rotation on removal is **mandatory**. The removed member is also dropped from rosters so members stop fanning out to them.
- **Revoke (1:1):** a party severs the friendship — discards the shared secret and refuses further messages, rendering the counterpart unable to communicate.

Either party/any member may initiate; the counterpart(s) auto-apply the change on receipt. Rotation/revocation requests travel **in-band** over the existing secure channel (or wait in the mailbox if a recipient is offline).

### 3.7 Membership changes (group)

- **Add a member:** the adder must already be friends with the newcomer (pairwise public keys exchanged). On add, the newcomer's profile is fanned out to all existing members, and each existing member's profile to the newcomer, establishing the all-pairs friendship the group requires. The current `Kg` is delivered to the newcomer sealed under the adder↔newcomer pairwise secret. Optionally rotate `Kg` on add.
- **Remove a member:** see §3.6 (mandatory rotation excluding the removed member).

### 3.8 Concurrent rotation

Two members may rotate simultaneously, producing two candidate keys. Resolution is deterministic: each key carries `(epoch, originator-id)`; the highest epoch wins, ties broken by lowest originator-id. Members converge after a brief `Rotating` state. Bounded edge case, not a redesign.

### 3.9 Threat model & honest limitations

- **The helper/VPS never sees plaintext or keys.** It handles rendezvous, blind relay, and an encrypted mailbox — ciphertext only. Even full relay of all traffic reveals only metadata (who talks to whom, and when), never content.
- **No forward secrecy:** a compromised current key exposes that conversation's history until the next rotation. Manual rotation is the mitigation; this is a deliberate v1 trade.
- **Removed group members retain past messages** they already received (unavoidable) but are cut off from all future messages.
- **Profile authenticity is trust-on-first-use:** users exchange profiles over a channel they trust; v1 does not add an out-of-band fingerprint-verification step (candidate for a later release).

## 4. Architecture

```
+-----------------------------------------------+
|  Preact + SCSS UI  (renders, never crypts)    |
|   LoginView / ConversationsList / ChatWindow  |
|   AddFriend(export/import) / GroupControls /   |
|   KeyControls (rotate / revoke / remove)       |
+----------------------+------------------------+
                       | Tauri IPC (typed commands + events)
+----------------------v------------------------+
|  Rust core  (all secrets live here)           |
|   identity / crypto / conversations / group / |
|   transport / mailbox / vault / commands       |
+----------------------+------------------------+
            | QUIC (iroh)            | HTTPS
   +--------v--------+      +--------v---------+
   |  friend's app   |      |  your VPS helper  |
   +-----------------+      | rendezvous /      |
                            | relay / mailbox    |
                            +--------------------+
```

**The seam that matters:** plaintext and private keys never cross the IPC boundary into the UI. The UI passes the core a recipient/conversation plus a string; the core derives keys, signs, seals, stores, and ships. This single rule is what makes "the UI is just a web page" safe.

## 5. Rust core — module breakdown (SOLID)

Each module has one responsibility, a narrow public interface, and is testable in isolation.

- **`identity`** — generates/loads the long-term X25519 and Ed25519 keypairs and iroh node identity; produces/parses the profile blob. *Depends on: vault.*
- **`crypto`** — pure functions, no I/O, no state: `derive_shared`, `seal`, `open`, `sign`, `verify`. Unit-tested against known vectors. *Depends on: nothing.*
- **`conversations`** — the roster store: create/list conversations, membership, current key reference, epoch. Generalises 1:1 and group. *Depends on: vault.*
- **`group`** — group key lifecycle: mint `Kg`, sealed-envelope distribution, add/remove member, rotation, revocation, concurrent-rotation resolution. Implements the `GroupKey` strategy of the `KeyAgreement` trait alongside `DirectKey`. *Depends on: crypto, conversations, transport, mailbox.*
- **`transport`** — wraps iroh: connect/listen, send/receive framed bytes, fan-out one ciphertext to many node addresses, surface online/offline events. *Depends on: iroh only.*
- **`mailbox`** — talks to the VPS helper: push ciphertext for offline recipients, pull on reconnect, ack-delete. *Depends on: transport identity only.*
- **`vault`** — the only module touching disk: SQLCipher gateway for messages, conversations, members, keys, settings — all encrypted at rest. *Depends on: the unlocked DB key.*
- **`commands`** — thin Tauri IPC layer mapping UI calls to modules and emitting events; no business logic of its own.

**DRY guarantees:** `crypto` is the only place that encrypts/signs; `vault` the only place that persists; `transport` the only place that touches the network. No concern is duplicated.

## 6. Data flow — sending a group message

```
UI: send("hello", conversation=GroupX)
  -> commands.send_message
    -> conversations: resolve current Kg + epoch + roster for GroupX
    -> crypto.sign(my_ed25519_priv, frame)        -> signature
    -> crypto.seal(Kg, "hello")                    -> ciphertext
    -> vault.store(outgoing, ciphertext)            (encrypted history)
    -> transport.fanout(roster):
         for each member:
            online?  yes -> transport.send(member)
                     no  -> mailbox.push(VPS, member)   (waits)
Recipient core: transport/mailbox receives frame
    -> crypto.verify(sender_ed25519_pub, frame)    (authenticity)
    -> crypto.open(Kg, ciphertext)                 -> "hello"
    -> vault.store(incoming) -> emit event -> ChatWindow renders
```

## 7. Identity, login & profiles

- **First run:** user sets a local password -> Argon2id derives the vault key -> SQLCipher vault created -> fresh X25519 + Ed25519 identity generated inside the vault.
- **Login:** password re-derives the vault key and unlocks the vault. Wrong password = vault stays sealed.
- **Auto-login (opt-in, off by default):** the vault key is stored in the OS keychain so the app opens without a prompt.
- **Add a friend:** *Export* produces the profile blob (copyable string + file). The friend *Imports* it; once both have imported each other, the first connection derives the pairwise secret and the 1:1 conversation goes live.
- **Create group:** select existing friends; a group conversation is created and `Kg` distributed (§3.4).

## 8. UI (Preact + SCSS)

Hierarchical SCSS, one `.scss` per component, real class names, theme tokens, no CSS-in-JS, tab indentation (width 4).

- **`LoginView`** — set/enter password; auto-login toggle.
- **`AppShell`** — two-pane layout: `ConversationsList` (left) + `ChatWindow` (right).
- **`ConversationsList`** — friends and groups together, each with a presence/status indicator.
- **`ChatWindow`** — message history, composer; for groups, a member roster with per-member presence.
- **`AddFriendModal`** — export/import tabs.
- **`GroupControls`** — create group, add member, remove member.
- **`KeyControls`** — Rotate / Revoke (and Remove member for groups), with a status badge: *Secure · Rotating · Offline · Revoked*.

---

## 9. Error handling

- A typed `CoreError` enum surfaced to the UI as friendly states.
- **Decryption/verification failure** -> explicit "message could not be verified" — never silently rendered.
- **Network drops** degrade a conversation to *Offline*, not a crash; messages queue (locally or in the mailbox).
- **Rotation in flight** -> *Rotating* state; messages buffered until the new epoch settles.

## 10. Testing strategy

- **`crypto`** — unit tests against known vectors for seal/open, sign/verify, ECDH derivation. TDD.
- **`group`** — simulated multi-party tests for key distribution, rotation, removal (revocation), and concurrent-rotation convergence. TDD.
- **`conversations` / `vault`** — round-trip persistence tests under SQLCipher.
- **Integration** — two (and three) cores exchanging messages through a local instance of the helper, covering direct connection, relay fallback, and offline mailbox delivery.

---

## 11. The VPS helper service

A small standalone Rust binary the user hosts on their own VPS. Three jobs, all blind to plaintext:

1. **Rendezvous** — peers register their current public node address; the helper introduces peers to each other.
2. **Relay** — when hole-punching fails, forwards ciphertext between peers (dumb pipe; sees only noise).
3. **Mailbox** — parks ciphertext for offline recipients, delivers on reconnect, deletes on ack.

Holds no accounts, no plaintext, no keys. Stateless of message content. (iroh provides much of rendezvous/relay; the mailbox is the bespoke addition.)

## 12. Implementation milestones

The full vision is specified above; implementation proceeds in verifiable milestones:

1. **Vault + identity + UI shell** — login, encrypted vault, identity generation, two-pane Preact layout (no networking yet).
2. **Profiles + 1:1 transport + sealing** — export/import, iroh direct connection, ECDH-derived key, signed + sealed messages, live 1:1 chat.
3. **Mailbox + offline delivery** — helper service, push/pull/ack, offline UX.
4. **Groups** — conversation generalisation already in place; add group key distribution, fan-out, group UI.
5. **Rotation & revocation** — manual rotate/revoke for both 1:1 and groups; member removal; concurrent-rotation resolution.
6. **Polish & README** — error states, status badges, per-OS install docs, helper hosting guide, add-friend/group walkthrough.
